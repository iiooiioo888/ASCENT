## 1. 定位

| 欄位 | 決策 |
| --- | --- |
| 名稱 | 帝國掘起 |
| 類型 | 無限發展的模擬經營 |
| 核心 | **生產鏈深度** |
| 勝利條件 | **無** |
| 遊玩 | **隨時可玩** |
| 玩家做 | 建造 + 管理 + 競爭 + 探索 |
| 平台 | 網頁 + 手機（同一套 React；手機以瀏覽器為主） |
| 商業 | 免費 + 內購（內購品項本階段不鎖定；不得做成 MVP 必做） |
| 團隊 | **1 人** |
| 在線規模 | **1000 人以內** |

| 玩家行為 | 含義 | MVP |
| --- | --- | --- |
| 建造 | 放置建築、升級、佔地擴張 | 能放 3–5 座並開工／停止／收取 |
| 管理 | 選擇生產方式、隊列、切換、專精 | 選定方式開工與收取；專精／切換成本可後置 |
| 競爭 | 玩家市場、多維排行榜、資源互助 | **不做** |
| 探索 | 解鎖新系統／層級／物品（資料驅動） | 僅農業切片 |

引擎原則（與 [生產系統正式設計](production-system.md)、[GDD 0001](gdd/0001-overview.md) 同義）：

- 引擎只認識規則與類型，**永不修改**規則。
- 資料驅動；生產方式由規則自動生成，禁止手寫孤兒方式。
- **不跳級**；層級與繼承圖是 **DAG**，禁止循環。繼承深度上限 10（R-INH6）。

## 3. 生產

| 項 | 決策 |
| --- | --- |
| 生產方式數量 | **無上限**（引擎不設硬頂；由規則自動生成） |
| 生成 | 規則 → `MethodGenerator` → `production_methods` |
| 切換 | 可切換，**有成本** |
| 循環 | **半自動**（核心產業迴圈可跑，不必全程點擊每一跳） |
| 隊列 | **有限制**（建築／玩家側開工隊列有上限，不是「方式目錄有上限」） |

切換順序：先結算當前方式 → 扣除切換成本 → 再套用新方式。成本不足則切換不成立，已入帳產出保留。MVP 可先不做切換。

| 項 | 決策 |

## 5. 時間

```
gameTime = startGameTime + (now - startRealTime) / 1000 × timeScale
```

`timeScale = 60`。`now` 與 `startRealTime` 為 Unix 毫秒。不持久化「當前遊戲時間」。**無加速**。懶結算；伺服器權威；冪等。權威游標為 `lastSettledAt`（真實時間）。不對每座建築每遊戲秒跑迴圈。客戶端僅顯示，判定以伺服器為準。

| 現實 | 遊戲 |
| --- | --- |
| 1 秒 | 60 秒 = 1 分鐘 |
| 1 分鐘 | 1 小時 |
| 1 小時 | 60 小時 |
| 1 日 | 60 日 |
| 24 分鐘 | 1 遊戲日（86400 遊戲秒）← **日長換算，不是離線上限** |
| **8 小時** | **480 遊戲小時 = 1,728,000 遊戲秒 = 20 遊戲日** ← **入帳離線上限** |

### 5.1 離線上限（產品定案）

**離線結算上限 = 8 現實小時。** ADR **不另定第二套上限**。GDD 若曾寫 `maxOfflineGameSec=86400`，該值只當日長／原稿紀錄，**入帳已被本檔覆寫**。

| 鍵 | 值 | 含義 |
| --- | --- | --- |
| `maxOfflineRealSec` | `28800` | 8 × 3600 **現實秒** |
| `timeScale` | `60` | 寫死 |
| `maxOfflineGameSec` | `1728000` | `28,800 × 60` = 480 遊戲小時 = **20 遊戲日** |

```
cappedRealDeltaSec = min(rawRealDeltaSec, 28800)
gameDeltaSec       = cappedRealDeltaSec × 60
```

寫入成功後 `lastSettledAt = nowReal`。上限外產能為 0。顯示用 `gameTime` 不因上限凍結。MVP：懶結算 + `lastSettledAt`；進頁／操作時補結算；可選 NestJS cron。**不強依 Redis**。

### 5.2 更正原稿誤算

產品意圖：**離線結算上限 = 8 現實小時**。時間公式維持 `/ 1000 × 60`。決策本身（離線繼續、有上限、無加速）全部保留。

原稿曾寫「8 小時現實時間 = 8×60×60=28800 遊戲秒 = 遊戲內 8 小時」。這把 8 小時換成秒後誤標成**遊戲秒**，等於把 1:60 讀成 1:1，**與時間比例矛盾，不入帳**。

正確換算：

- 8 現實小時 = 28,800 **現實秒**
- 遊戲秒 = 28,800 × 60 = **1,728,000**
- = 遊戲內 480 小時 = **20 遊戲日**

| 讀法 | 數字 | 本檔 |
| --- | --- | --- |
| **入帳權威** | 8 現實小時 = 28,800 **現實秒** × 60 = **1,728,000 遊戲秒** = 480 遊戲小時 = 20 遊戲日 | **採用** |
| 原稿括號 | 28,800 **遊戲秒**（= 8 遊戲小時 = 8 現實分鐘） | **廢棄** |
| 「也等於遊戲 8 小時」 | 把 1:60 讀成 1:1 | **不採用** |

GDD 原稿 `maxOfflineGameSec=86400` 保留為日長：1 遊戲日 = 24 現實分鐘。入帳裁切用 `maxOfflineRealSec=28800`。ADR 0001 不另定第二套上限。NestJS、Prisma、PostgreSQL、懶結算、伺服器權威、Phaser 不進核心，維持不變。

## 6. 互動

玩家市場、多維排行榜、資源互助：目標可有，**非 MVP**。不得為它們在 MVP 引入登入、WebSocket 或 Redis。AI 訂單見 [gdd/ai-orders.md](gdd/ai-orders.md)，不在 MVP。

## 7. 優先級

**生產鏈深度 > 數值平衡 > 視覺 > 玩家互動 > 擴展性 > 上線速度**

問卷原編號（僅溯源）：3 > 4 > 2 > 1 > 5 > 6。

對應單人原則：現成 > 自寫、單體 > 微服務、一庫 > 拆分、手動 > 自動化、簡單 > 複雜。

不得為了上線速度或擴展性砍生產鏈深度。

## 10. 單人技術約束

### 10.1 原文（保留）

| 項 | 系統定義原文 |
| --- | --- |
| 執行環境 | Node.js + TypeScript |
| 主庫 | PostgreSQL 單一實例 |
| Redis | 初期可選、可不用 |
| 前端 | React + TypeScript + Vite |
| 部署 | Railway / Render 單一服務（**建議，不是供應商鎖定**） |
| 認證 | 簡單 JWT，無第三方 |
| WebSocket | 初期不用 |
| 原則 | 能用現成不自寫、能單體不微服務、能一個資料庫不拆、能手動不自動化、能簡單不複雜 |
| 規模 | 單體、單一 PostgreSQL、1000 人以內 |

MVP **無登入**；JWT 在玩家互動／多存檔之前才做。[ADR 0001](adr/0001-tech-stack.md) **不**因此改成 OAuth。

### 10.2 與 ADR 0001 不衝突（目標 vs MVP）

技術棧**最終定案不改**：TypeScript 全棧、React+Vite、NestJS、PostgreSQL+JSONB、Prisma、Redis+BullMQ、Socket.IO、Docker Compose；Phaser 不進核心。不得從 ADR 刪 Redis 或 Socket.IO。讀法是「目標保留、MVP 可關」。**不改成 Fastify。**

MVP 技術切片：**NestJS + PostgreSQL + Prisma + HTTP**。Redis／BullMQ／WebSocket 後置。懶結算在讀取／進頁時補算（其後才是登入時補算）。

| 主題 | 目標（ADR 0001，**保留**） | MVP／單人初期 | 何時才引入 |
| --- | --- | --- | --- |
| Redis + BullMQ | Session、熱狀態、離線補算與 tick；Redis 不是主庫 | **可不啟用**；結算走 HTTP；不強依 Redis | 請求路徑補算過慢；需要未發請求時的 tick 且 NestJS 定時器不夠用；需要 Session／熱狀態／排行榜；併發接近 1000 人且同步結算堵住 HTTP |
| Socket.IO | 推已入帳結果 | **不用 WebSocket**；HTTP 輪詢或進頁 GET | 輪詢負載或停留頁完工反饋不可接受；需要 `settlement`／`production_complete` 推送；市場／互助等即時狀態 |
| 部署 | 本機 Docker Compose；雲端不鎖定 | 初期可單一服務；Railway／Render 僅建議 | 雲端供應商另開 ADR 才鎖定 |
| 認證 | 不改成 OAuth | **MVP 無登入**；其後簡單 JWT | 需要多玩家身分、市場或排行榜時 |

引入 Redis 後，BullMQ 必須呼叫與 `inventory` 相同的結算入口。引入 Socket.IO 後，Gateway 只推已入帳結果。Cron 與 tick 都不得另寫一套扣庫公式。

### 10.3 為何與單人約束不衝突

「Redis 初期可選」「初期不用 WebSocket」是**單人期運維負擔**，不是「目標棧作廢」。分期 = 同一 NestJS 單體上先關閉佇列與推送。引入時不換核心框架（**Fastify 仍為否決項**）、不改 1:60、不把「初期不用」讀成「永遠刪掉」。

## 11. 架構圖

### 11.1 MVP（啟用路徑）

```
React + TypeScript + Vite
        │  HTTP /api/v1（輪詢或進頁 GET）
        ▼
Node.js + NestJS 單體
  catalog / rules / simulation / inventory
  可選 NestJS 定時器（呼叫與 inventory 同一結算入口）
        │
        ▼
PostgreSQL 單實例（Prisma）
```

### 11.2 目標棧（括號為 MVP 關閉件）

```
React + TS + Vite ──HTTP──► NestJS 單體
                              catalog / rules / simulation / inventory
                              realtime 〔目標；MVP 關〕
                              jobs     〔目標；MVP 關〕
                         ├── PostgreSQL + Prisma
                         └── Redis+BullMQ 〔MVP 可不啟〕
```

禁止再建模組名叫 `core`。對照：[architecture/0001-module-boundaries.md](architecture/0001-module-boundaries.md)。
